01 · why this exists

Every published NIDS paper does this differently, or not at all.

A model that scores 99% on a benchmark can still be learning nothing about real attacks, if the benchmark is riddled with duplicate rows, leaked features, or a train/test split with the same session on both sides. Researchers have caught these problems before, one at a time, in one-off notebooks tied to one dataset. IDS2Eval turns that methodology into software you run on your own data, in minutes, from a config file.

Status quo

A one-off analysis notebook

Re-derived per paper, per dataset. Findings aren't reusable, and rarely open-sourced in a runnable form.

Generic tools

AutoML (PyCaret, AutoGluon, TPOT)

Breadth of algorithms, but no IDS-specific data-quality checks: leakage and homogeneity aren't in scope.

IDS2Eval

Config-driven, IDS-specific, reusable

16 checks + 14-classifier benchmark from one YAML file. Point it at a CSV, get a finding with a status and a number.

03 · the checks

Sixteen checks. Two kinds of finding, two ways to run.

Every check returns {check, status, summary, details}, a flag or warning names the specific, checkable signature behind it, not a vague quality score. Every run rolls these into a citable SCORECARD.html: pass, passed with warnings, or failed. Pass/fail rule and full writeup: guide/checks.md.

15
Always on, zero setup
4
Opt-in, deeper analysis
17
Measure this run's data
2
Report a documented fact

Checks measure this run's own data and can be reacted to: drop a column, resample, switch split modes. The scorecard gives each a status for the raw data and the cleaned data, side by side. Known issue checks look only at the dataset's name or column names, never the data, so a single status is all they get: nothing in your config changes what they find. Always on runs by default, no extra setup. Opt-in needs a second dataset, a declared timestamp column, or accepts heavier compute.

dedup_check Exact feature-space duplicates within and across train/test: memorization, not generalization. ChecksAlways on
label_conflict_check Groups rows by identical features and flags any group that maps to more than one label. ChecksAlways on
near_duplicate_class_check Extends label_conflict_check to near-identical features across two classes, not only exact matches. ChecksAlways on
leakage_screen Fits a fast RandomForest and inspects its own feature importances to catch shortcut learning. ChecksAlways on
one_rule_check Fits a single depth-one decision tree and reports the winning rule in plain language. ChecksAlways on
identity_column_flag Standalone predictive power of IP/port/MAC-like columns you declare as identity columns. ChecksAlways on
port_protocol_shortcut_check Standalone predictive power of a declared port column combined with a protocol column, as a pair. ChecksAlways on
temporal_leakage_check Tests whether a configured timestamp column alone predicts the label. ChecksAlways on
flow_group_leakage_check Hashes a declared flow identity (e.g. a 5-tuple) and flags any identity present on both sides of the split. ChecksAlways on
homogeneity_test Nearest-neighbor distance vs. a same-set control, to separate real leakage from class homogeneity. ChecksAlways on
resplit_falsification A session/time-grouped resplit that makes session-correlated leakage structurally impossible. ChecksAlways on
class_distribution_report Per-class counts, shares, and imbalance ratio, before and after dedup. ChecksAlways on
low_cardinality_warning Flags identity-like columns with suspiciously few unique values relative to the split. ChecksAlways on
data_integrity_check Missing labels, missing or constant features, and plus-or-minus-infinity values. ChecksAlways on
schema_fingerprint_check Column names match a flow extractor with a documented calculation bug. Known issueAlways on
synthetic_realism_check Trains a domain classifier to distinguish this dataset from a reference real-traffic sample. ChecksOpt-in
cross_dataset_drift_check Trains on this dataset, evaluates on a reference dataset in a unified feature space. ChecksOpt-in
known_issue_lookup A curated table of documented, published problems for this exact dataset. Known issueOpt-in
seed_sensitivity_check Re-fits leakage_screen and one_rule_check across five seeds and flags an unstable verdict. ChecksOpt-in

05 · configure it

One YAML file. No code required for the common case.

Every field is documented in configs/schema.yaml; worked examples in guide/configuration.md.

# my_config.yaml
dataset:
  name: my-dataset
  raw_files: ["data.csv"]
schema:
  label_column: Label
preprocessing:
  dedup: true
  sampling:
    binary: [none, smote, smoteenn]
classifiers:
  list: [RandomForest, XGBoost]
  tuning: true
random_seed: 42
06 · scope

What this deliberately doesn't do.

Disclosed on purpose, not a hidden limitations paragraph three pages into a README.

Out of scope, on purpose

  • Feature engineering. No imputation, feature selection, or dimensionality reduction. Dedicated tools already do this well; IDS2Eval audits and benchmarks the features you give it.
  • Deep hyperparameter search. classifiers.tuning runs a fixed grid, on purpose, to keep classifier comparisons fair. Bring your own Bayesian search if you need one.
  • The staged-cascade detection architecture from this project's companion research paper. This tool ships the reusable audit and benchmark methodology, not the novel architecture built on top of it.
