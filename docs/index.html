01 · why this exists

Every published NIDS paper does this differently — or not at all.

A model that scores 99% on a benchmark can still be learning nothing about real attacks, if the benchmark is riddled with duplicate rows, leaked features, or a train/test split with the same session on both sides. Researchers have caught these problems before, one at a time, in one-off notebooks tied to one dataset. IDS2Eval turns that methodology into software you run on your own data, in minutes, from a config file.

Status quo

A one-off analysis notebook

Re-derived per paper, per dataset. Findings aren't reusable, and rarely open-sourced in a runnable form.

Generic tools

AutoML (PyCaret, AutoGluon, TPOT)

Breadth of algorithms, but no IDS-specific data-quality checks — leakage and homogeneity aren't in scope.

IDS2Eval

Config-driven, IDS-specific, reusable

16 checks + 14-classifier benchmark from one YAML file. Point it at a CSV, get a finding with a status and a number.

03 · the checks

Sixteen checks. Two kinds of finding.

Every check returns {check, status, summary, details}, a flag or warning names the specific, checkable signature behind it, not a vague quality score. Every run rolls these into a citable SCORECARD.html: pass, passed with warnings, or failed. Full writeup for all 16 and the scorecard's pass/fail rule: guide/checks.md.

14 checks

Measure this run's data

Each one can be reacted to: drop a column, resample, switch split modes. The scorecard gives each a status for the raw data and a status for the cleaned data, side by side, so a problem dedup fixed is visible, not hidden.

v1 · always on
dedup_check

Exact feature-space duplicates within and across train/test: memorization, not generalization.

v1 · always on
label_conflict_check

Same features, different labels: the ground truth contradicting itself.

v1 · always on
leakage_screen

One feature quietly carrying the whole classification problem.

2 checks

Report a documented fact

Look only at the dataset's name or its column names, never the data itself, so cleaning can't change what they find. A single status, no config of yours fixes these.

v1 · always on
schema_fingerprint_check

Column names match a flow extractor with a documented calculation bug.

v2 · opt-in
known_issue_lookup

A curated table of published problems for this exact dataset.

Plus 11 more: one_rule_check, temporal_leakage_check, identity_column_flag, homogeneity_test, resplit_falsification, class_distribution_report, low_cardinality_warning, data_integrity_check, synthetic_realism_check, cross_dataset_drift_check, seed_sensitivity_check. All in guide/checks.md.

Selected findings, on real data → full real scorecard, every artifact

flag — real finding

leakage_screen

Fits a fast RandomForest and inspects its own feature importances. Independently reproduced Flood et al. 2024's finding that Destination Port alone hits near-perfect accuracy across CIC-IDS2018 — confirmed on the real, official distribution.

ok — settled by experiment

resplit_falsification

A session-grouped resplit that makes session-correlated leakage structurally impossible. On CIC-IDS2018's near-saturation accuracy, the grouped resplit reproduced the random split's accuracy to within 0.003 percentage points.

flag → ok after dedup

dedup_check

Exact feature-space duplicates between train and test. On real UNSW-NB15 data: 42.38% train duplication before cleanup, correctly dropped to 0% after — measured twice, not assumed. See the real run →

warning — real shift

class_distribution_report

Per-class counts and imbalance ratio, before and after dedup. On UNSW-NB15 the ratio shifted from 2:1 to roughly 1:1 after deduplication — duplicated rows were disproportionately one class. See the real run →

flag: real finding

label_conflict_check

Groups rows by identical features and checks whether they share one label. On CSE-CIC-IDS2018, found that every one of FTP-BruteForce's 35 distinct feature vectors is also labelled DoS-SlowHTTPTest: identical flows, two labels. See the real run →

05 · configure it

One YAML file. No code required for the common case.

Every field is documented in configs/schema.yaml; worked examples in guide/configuration.md.

# my_config.yaml
dataset:
  name: my-dataset
  raw_files: ["data.csv"]
schema:
  label_column: Label
preprocessing:
  dedup: true
  sampling:
    binary: [none, smote, smoteenn]
classifiers:
  list: [RandomForest, XGBoost]
  tuning: true
random_seed: 42
06 · scope

What this deliberately doesn't do.

Disclosed on purpose, not a hidden limitations paragraph three pages into a README.

Out of scope, on purpose

  • Feature engineering. No imputation, feature selection, or dimensionality reduction. Dedicated tools already do this well; IDS2Eval audits and benchmarks the features you give it.
  • Deep hyperparameter search. classifiers.tuning runs a fixed grid, on purpose, to keep classifier comparisons fair. Bring your own Bayesian search if you need one.
  • The staged-cascade detection architecture from this project's companion research paper. This tool ships the reusable audit and benchmark methodology, not the novel architecture built on top of it.
